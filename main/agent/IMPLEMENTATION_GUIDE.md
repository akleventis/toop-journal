# Agent Knowledge Index — Implementation Guide

Pre-parsed knowledge layer for the Book of Toop AI agent.
Built through design sessions May 2026. This document is the source of truth for the build.

---

## The Problem This Solves

The current agent does: FTS5 keyword search → dump 25 raw HTML entries into context → hope the model synthesizes correctly. With 7+ years of entries this produces hallucinations, missed connections, and shallow answers.

The fix: build a structured knowledge layer through a series of specialized crawls — each focused on a different domain (people, locations, themes, etc.), run in sequence, and refinable by re-running any pass. The agent queries facts first, navigates to targeted entries, then pulls raw text only for evidence and quotes.

---

## Three-Layer Retrieval

```
Layer 1 — Knowledge index (pre-built, fast, low token cost)
  Query structured facts: who is this person, what period was this, what themes
  Best for: orientation, navigation, answering factual questions directly

Layer 2 — FTS5 (existing, keyword search)
  Discover which entries mention a topic when the index doesn't have it pre-built
  Best for: open-ended discovery, topics not covered by a specific crawl

Layer 3 — Raw entries (always available, full text)
  Read individual entries directly — by date, by ID, or by range
  Used for: verbatim quotes, evidence, and natural reading
  The agent can pull and read any entry at any point in its reasoning,
  not just after consulting the index first
```

The layers are tools, not a strict pipeline. The agent picks whichever combination serves the question. A simple date lookup goes straight to Layer 3. A broad "who was I in 2021" question starts at Layer 1, navigates to relevant entry IDs, then reads those entries directly. The index makes retrieval smarter — it doesn't replace reading.

## New Tables

All knowledge tables live in `main/agent/knowledge-db.ts` — completely separate from `main/db/sqlite.ts`. `knowledge-db.ts` opens its own read-write connection to the same DB file and owns all knowledge table creation, schema, and CRUD. Nothing knowledge-related touches `sqlite.ts`.

Table creation happens in `initKnowledgeDb()`, called from `main.ts` at startup alongside the existing DB init.

### Crawl infrastructure

**`crawl_state_t`** — tracks progress per crawl type and pass
```
crawl_type                TEXT    -- 'people' | 'locations' | 'entry_metadata' | etc.
pass                      INTEGER -- 1 (blind) | 2 (informed) | 3+ (verification)
pass_type                 TEXT    -- 'extraction' | 'verification'
phase                     TEXT    -- 'idle' | 'running' | 'awaiting_qa' | 'qa_complete' | 'complete' | 'failed'
last_run                  INTEGER -- ms timestamp
entries_processed         INTEGER
last_processed_entry_id   TEXT    -- entry_id of last successfully processed entry; resume from here on restart
PRIMARY KEY (crawl_type, pass)
```

**`setup_questions_t`** — Q&A generated by blind crawl, answered by user
```
id          INTEGER PRIMARY KEY
crawl_type  TEXT
question    TEXT    -- "Are Alex and Yeezy the same person?"
context     TEXT    -- why we're asking, shown optionally to user
answer      TEXT    -- null until answered
skipped     INTEGER -- boolean
answered_at INTEGER
sort_rank   INTEGER -- higher = more combined mentions = shown first (no cap on questions)
```

## Crawl Architecture

### Pass types

Two fundamentally different kinds of passes. The crawl runner checks `pass_type` to know what each pass does:

**Extraction passes** (`pass_type = 'extraction'`)
Read raw journal entries → write to knowledge tables. Heavy and slow — the model processes HTML entry content one at a time. Only passes 1 and 2 are extraction passes.

**Verification passes** (`pass_type = 'verification'`)
Read knowledge tables → refine knowledge tables. No raw entries needed. The model reasons over clean structured data it already produced, which is a significantly easier job. Faster, cheaper, and compounds on previous work. Pass 3 and beyond are all verification passes.

Each re-run of a verification pass makes the index richer without ever touching raw entries again.

---

### Full pass sequence

```
Pass 1 — Extraction (blind)
  pass_type = 'extraction'
  Reads raw entries in timestamp order, one per Ollama call
  Pure extraction — marks low-confidence items, no questions
  Writes to knowledge tables with confidence levels
  Resumable: last_processed_entry_id written after each entry
  Sets phase = 'awaiting_reasoning' when complete

Agent reasoning pass
  Runs as agent loop in question-generation mode (not a crawl pass)
  Read-only tools across all knowledge tables
  Only write: write_question tool → setup_questions_t
  Generates Q&A from uncertainties in the extracted data
  Sets phase = 'awaiting_qa'

Q&A session
  User answers all questions
  Answers written to setup_questions_t
  Sets phase = 'qa_complete'

Pass 2 — Extraction (informed)
  pass_type = 'extraction'
  Re-reads raw entries with Q&A answers injected into prompt as verified facts
  Overwrites knowledge tables with corrected, high-confidence data
  Resumable via same pattern
  Sets phase = 'complete'

Pass 3+ — Verification
  pass_type = 'verification'
  Reads knowledge tables only — never touches raw entries again
  Model refines, connects, and enriches what's already there
  Examples per crawl type:
    people:    resolve remaining low-confidence names using now-known aliases
    relations: check arcs for gaps or contradictions
    themes:    merge overlapping themes, find missing connections
    metadata:  backfill entries that had 0 key sentences on first pass
  Each run compounds — index gets richer without re-extraction cost
  User can trigger from UI: "Run another pass to improve accuracy"
```

Stop/resume is free for all extraction passes: write `last_processed_entry_id` after every entry, resume by querying entries after that timestamp. Verification passes operate on tables not entries, so they're inherently resumable at the table level.

### Why the agent does question generation, not the crawl model

The crawl model only sees one entry at a time. It cannot notice that "Alex" appears 34 times and "Yeezy" appears 127 times in overlapping contexts — it has no cross-entry view. Questions that require reasoning across the full dataset must come from something that can see the full dataset.

The agent reasoning pass reads from `mentions_t`, `entry_metadata_t`, etc. via tools and reasons across everything extracted. It is the right tool for this job. The crawl model stays simple — pure extraction, no reasoning burden.

The only write tool ever exposed to any model: `write_question(question, context, sort_rank)` — writes to `setup_questions_t` only. Nothing else.

Examples of what the reasoning agent finds and asks:

| Finding | Question generated |
|---|---|
| "Alex" 34×, "Yeezy" 127× in overlapping contexts | "Are 'Alex' and 'Yeezy' the same person?" |
| "drove to the coast" 8× in 2019–2021, no state | "Around 2020, which coast were you near?" |
| "left the job" with no employer named | "What job did you leave in early 2022?" |
| "Marcus" appears once, no relationship context | "Who is Marcus — how do you know him?" |

### Crawl order (dependency chain)

```
── Extraction pass 1 (blind) ──────────────────────────────────
1.  people
2.  locations + life_periods
3.  entry_metadata
4.  work_career, health, hobbies, social
5.  relationships, milestones
6.  recurring_themes, beliefs_values

── Agent reasoning pass ────────────────────────────────────────
7.  reads all tables → generates setup_questions_t

── Q&A ─────────────────────────────────────────────────────────
8.  user answers all questions

── Extraction pass 2 (informed) ────────────────────────────────
9.  all crawls re-run with Q&A answers injected
10. life_chapters synthesis (reads all finalized tables)

── Verification passes (pass 3+, on demand or scheduled) ───────
11. people verification    — resolve remaining low-confidence names
12. metadata verification  — backfill 0-sentence entries, improve weak extractions
13. relationships          — check arcs for gaps, contradictions
14. themes + beliefs       — merge overlapping, find missing connections
    ... each pass compounds, no raw entries read
```

Verification passes (step 11+) can be triggered by the user at any time from the UI: "Run another pass to improve accuracy." Each one makes the index richer without re-extraction cost. Running 3–4 total passes over time produces a significantly better index than any single run.

### Incremental sync

Every time the agent is opened. On every `/agent` mount:
1. Find entries needing re-crawl: `SELECT * FROM entries_t e JOIN entry_metadata_t m ON e.id = m.entry_id WHERE e.lastModified > m.crawled_at`  — plus any entries not yet in `entry_metadata_t` at all
2. If any found → run incremental crawls automatically in the background
3. Chat is available immediately — sync runs alongside it

For one-to-one tables (`entry_metadata_t`): `INSERT OR REPLACE` handles upsert cleanly.
For one-to-many tables (`mentions_t`): crawl runner code (not the model) runs `DELETE WHERE entry_id = ?` before re-inserting. Required because an edited entry may now mention fewer people than before.

The model only ever has access to read-only tools. All writes, deletes, and upserts happen exclusively in crawl runner code in the main process — never via a model-callable tool.

Users who start with zero entries get a fully up-to-date index automatically. The index grows with the journal.

## Key Sentence Extraction Rules

These rules go into the extraction prompt verbatim. The model does not use taste or judgment — it applies this checklist.

### Extract a sentence if it contains ANY of:
1. A named person, place, or thing
2. A decision or resolution ("I decided", "we agreed", "I'm done with", "I'm going to")
3. A temporal significance marker ("first time", "finally", "again", "never", "last time")
4. An emotion anchored to something specific — NOT "I felt sad" but "I felt sad about X"
5. A direct question ("why do I keep doing this?", "what am I doing?")

### Context rule
If the subject of the sentence is not a named entity or "I", include the preceding sentence as a unit. Extract both as one entry in `key_sentences`.

> "He said yes finally." → grab preceding sentence too → ["I asked Jake about moving in together.", "He said yes finally."]

### Volume rules
- No cap on key sentences per entry
- Entries with 10+ matches → set `milestone_flag = 1`
- Entries with 0 matches → store null in `key_sentences`, this is valid data (low-content day)

### Do NOT extract:
- Generic observations: "It was a nice day."
- Emotion without an anchor: "I felt sad." (needs "I felt sad about X")
- Pure filler: "Anyway...", "I don't know.", "Yeah."
- Weather alone: "It was cold and rainy."

### Prompt structure
1. Explicit checklist (the 5 rules above)
2. Negative examples (the do-not-extract list)
3. One worked example showing the unnamed-subject rule
4. Known aliases injected at the top on pass 2+: "Known people: Alex / Yeezy (same person), Jake / Jacob (same person)"

One entry per Ollama call. Never batch multiple entries — the model conflates facts.

## People Crawl (most complex, runs first)

### Pass 1 — blind extraction
For each entry, prompt asks: "List every person's name mentioned in this entry. For each, include the exact name as written and a 1-sentence context snippet showing how they're referenced."

Output → `mentions_t` (raw_name, entry_id, context_snippet). `person_id` is null until pass 2.

### Alias detection — handled by agent reasoning pass

After all blind crawls complete, the agent reasoning pass reads `mentions_t` and generates questions about names that might be the same person. The people crawl itself does not generate questions — it just marks low-confidence names with `"confidence": "low"` in the output JSON and moves on.

The agent sees all 300+ Yeezy mentions and all 34 Alex mentions in aggregate, notices the overlap, and writes a question to `setup_questions_t`. No algorithm, no clustering — the agent reasons about it the same way a human would reading the data.

### Pass 2 — informed re-crawl
Answers from `setup_questions_t` injected into prompt as ground truth. `people_t` updated with canonical names, aliases, first/last entry IDs, total mentions, confidence = 'high'.

`mentions_t.person_id` backfilled for all resolved aliases.

## New Agent Tools (added after crawl is complete)

These replace `search_journal` as the primary retrieval path.

**`lookup_person(name)`**
Returns: canonical name, all aliases, relationship type, first/last seen, total mentions, arc summary, list of entry IDs.
Agent uses entry IDs to then call `get_entries_by_ids` for quotes.

**`get_life_period(date)`**
Returns: which life period/chapter the user was in at a given date.
"March 2022" → "Military era, Goldsboro, NC — Apr 2021 to Aug 2023"

**`get_entries_by_ids(ids[])`**
Takes an array of entry IDs, returns full raw content for each.
This is the evidence pull. Agent quotes directly from these.
Replaces the current pattern of dumping 25 FTS results into context.

**`search_entry_metadata(filters)`**
Query `entry_metadata_t` by topic, emotion, activity, conflict_flag, milestone_flag, date range.
Returns matching entry IDs + key_sentences snippets.
The model uses this to navigate, then calls `get_entries_by_ids` for full content.

**`get_milestones(date_range?)`**
Returns milestone events optionally filtered by date range.

**`search_journal`** (existing — demoted to fallback)
Still available for keyword queries not covered by the index. No longer the workhorse.

## Crawl Output Schemas

Every crawl prompt instructs the model to return valid JSON matching the schema below. The crawl runner parses the JSON and writes to the DB — the model never writes directly.

**Important:** The 7b model occasionally produces malformed JSON. The crawl runner must:
1. Attempt `JSON.parse(response)`
2. On failure → log raw output, skip the entry, mark it for retry
3. Never crash the crawl on a single bad response

Two types of crawls: **per-entry** (called once per entry, processes in timestamp order) and **synthesis** (called once after all entries are processed, reads from existing knowledge tables).

---

### People crawl — pass 1 (per-entry)

Pure extraction only. Runs once per entry — 300 entries with Yeezy = 300 results accumulating into `mentions_t`. One context snippet per mention within the entry. Marks uncertain names with `"confidence": "low"` but does not generate questions — that is the agent reasoning pass's job.

```json
{
  "entry_id": "jun.14.2025",
  "entry_date": "Jun 14, 2025",
  "people": [
    {
      "raw_name": "Yeezy",
      "confidence": "high",
      "context_snippets": [
        "caught up with Yeezy on the drive over",
        "Yeezy said he might come visit next month"
      ]
    },
    {
      "raw_name": "A",
      "confidence": "low",
      "context_snippets": [
        "A hit me up earlier"
      ]
    }
  ]
}
```
Empty entry: `{ "entry_id": "...", "entry_date": "...", "people": [] }`

`mentions_t` gets one row per snippet, with `entry_date` stored directly. The agent reasoning pass can then query temporal distribution of any name without joins — "Alex: 34 mentions 2019–2021, Yeezy: 127 mentions 2021–present" comes from a single `mentions_t` scan.

### Agent reasoning pass — write_question tool

The agent reasoning pass does not return JSON. It runs as a tool loop, calling `write_question` for each uncertainty it finds. This is the only write tool ever exposed to any model.

```
Tool: write_question
Arguments:
  question   TEXT  -- "Are 'Alex' and 'Yeezy' the same person?"
  context    TEXT  -- "Alex: 34 mentions (2019–2021). Yeezy: 127 mentions (2021–present)."
  sort_rank  INTEGER -- combined mention count or confidence impact score
```

The agent reads from knowledge tables via existing read-only tools, reasons across the full dataset, and calls `write_question` for each uncertainty. When done it returns a summary of how many questions were written. No other writes occur.

## Build Order

The core infrastructure is a generic crawl runner that accepts a prompt + output schema and processes entries. Each crawl type is not a separate file — it's a different prompt fed into the same runner. The real work is prompt tuning, not building N separate crawl files.

```
1. knowledge-db.ts        — table creation + all read/write functions
2. crawl-runner.ts        — generic: accepts prompt + schema, processes entries in order,
                            writes last_processed_entry_id, resumable, emits progress
3. People prompt           — first prompt to tune against real entries → mentions_t
4. reasoning-pass.ts      — agent loop in question-generation mode, write_question tool
5. AgentQA.tsx + IPC      — Q&A screen, banner, setup_questions_t read/write
6. AgentSetup.tsx         — progress screen, first-visit detection
7. Remaining prompts      — metadata, locations, work, health, hobbies, social,
                            relationships, milestones, themes, beliefs
                            (each is a prompt config + target table, not a new file)
8. Verification prompts   — one per crawl type, reads tables not entries
9. knowledge-tools.ts     — new agent tools (lookup_person, get_entries_by_ids, etc.)
10. agent.ts + prompt     — swap in new tools, update system prompt
```

Steps 3 and 7 are where most of the actual time goes — getting prompts to produce clean, consistent JSON against real journal entries requires iteration. The infrastructure (steps 1, 2, 4–6) just needs to be solid enough to support that iteration loop quickly.

## Models

Two models — different jobs. Both constants exported from `ollama.ts`.

| Constant | Model | Used for |
|---|---|---|
| `CHAT_MODEL` | `qwen2.5:7b-instruct` | Chat agent — fast, responsive |
| `CRAWL_MODEL` | `qwen2.5:14b-instruct` | All extraction + verification passes |

Extraction runs once and quality is permanent until a re-crawl. Using a stronger model here directly addresses the 7b quality ceiling — 14b is noticeably better at consistent structured extraction. Speed doesn't matter for crawls; they run in the background.

## Context Window

Both models default to 32k context in Ollama. Set `num_ctx: 131072` in API request options for ~128k tokens:

```ts
options: { num_ctx: 131072 }
```

Memory cost: ~+1-2GB on top of model weight. Fine for any M-series Mac with 16GB+ RAM.

## Watch-outs

- The model is read-only, enforced at the code layer. All writes, deletes, and upserts are crawl runner or knowledge-db.ts code only — never exposed as model-callable tools.
- `knowledge_conflicts_t` is a different table from `conflicts_t` (which is cloud sync conflicts). Never confuse them.
- All JSON columns (people_mentioned, activities, etc.) stored as JSON strings — parse on read, stringify on write.
- The crawl runner lives in the main process, not tied to renderer lifecycle. Progress updates push to renderer via IPC. Navigating away from /agent does not interrupt a running crawl.
- Pass 2 of any crawl overwrites pass 1 data. Idempotent — safe to re-run.
- `word_count` in `entry_metadata_t` is counted from stripped plain text, not raw HTML.
- Aliases in `people_t` include all historical names in chronological order — useful for understanding name transitions over time.
